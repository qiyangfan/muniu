# ADR-0005:产品定位——数据面网关,单机与集群双形态;平台能力归独立控制面

- 状态:已接受(2026-09-11)
- 背景人:终局目标是公开注册、真实计费收款、高可用的平台型产品;本 ADR 裁决 muniu 在其中的定位。

## 决策

muniu 定位为 **LLM 网关数据面**,两种部署形态皆为一等公民:

- **形态 A · standalone(默认,现状)**:单二进制 + 内嵌 SQLite,零运维依赖,自托管开箱即用;
- **形态 B · managed/cluster**:muniu 实例为**无状态数据面副本**(LB 后水平扩展),权威状态(用户/钱包/渠道/价目)由**独立控制面产品**(新仓库,PostgreSQL 为权威存储)下发;SQLite 降级为本地缓冲与审计兜底(计量行绝不丢:断网缓冲、恢复续传)。

**平台能力(用户注册/钱包/支付/渠道管理门户)不在本仓实现**,归控制面产品另立宪法。muniu 宪法非目标相应修订:商业化与用户门户仍不做,「高可用集群形态」从非目标移出(集群数据面形态按本 ADR 演进)。

## 理由(参考头部开源项目的同类分岔)

- **Envoy + xDS / Kong DB-less**:数据面纯粹、控制面分离是现代 L7 网关的规范形态;Kong 自 1.1 起把 DB-less 无状态模式设为推荐默认——连最早「内嵌数据库配置」的网关都在往这个方向迁;
- **Nacos**:standalone 内嵌 Derby、cluster 强制外部 MySQL——「单机内嵌存储、集群外部权威库」的双形态直系先例,形态切换不换产品;
- **Grafana**:内嵌默认 + PG/MySQL 可选,HA = 共享库 + 多无状态副本——单机体验与商业 HA 并存且互相成全;
- **Gitea**(反例佐证):刻意不做集群把极简单机做到极致照样顶流——说明选型自由存在,但**选了单机就要认这条边界**;muniu 的终局目标在集群侧,故不能抄它;
- **one-api / LiteLLM / Portkey / Helicone**(同赛道):one-api 单体+SQLite 起家,多节点要 MySQL+Redis 且账本一致性靠约定;LiteLLM 与 Portkey/Helicone 均拆为「无状态网关 + DB 支撑的控制面」。品类头部在向分离式收敛,后来者不必重走弯路。

否决「muniu 单体平台化」的四个理由:

1. **爆炸半径与迭代节奏冲突**:钱包/支付代码按产品节奏迭代且带合规负担,转发路径要性能与稳定纪律——耦合则互相拖累;
2. **安全面矛盾**:公开平台的攻击面(注册/支付 webhook/用户门户)与网关应有的最小暴露面相反;分离后网关可做到**纯拉取同步、零管理入站暴露**;
3. **HA 本来就要求无状态副本**:单体内嵌钱包 + SQLite 做不了真 HA,分离在关键路径上——应作为架构做,而不是事后补丁;
4. **宪法连续性与开源卡位**:muniu 保持「基建 + 品质纪律」定位,数据面性能、协议 conformance 资产、零浮点计价是差异化护城河;转型单体意味着与 one-api/New API 在功能红海里同质化追跑。

## 演进项(muniu 仓,按序)

1. **P1 状态分层**:①自校验 API key(HMAC 签名形态,网关离线验真,吊销经版本同步收敛)与现有查库 key 并存;②配置源抽象——providers/model_routes/pricing 由「文件(现状)或控制面版本化拉取」双驱动,推广 pricing directory 的原子热替换模式;③计量汇插拔(本地 SQLite / 控制面 ingest / 直写 PG),本地 SQLite 永远兜底缓冲;
2. **P1.5 可观测**:`/metrics`(Prometheus 文本协议;client 依赖按白名单制走 ADR 增补);
3. **P2 参考部署**:cluster 形态的 compose/k8s manifests 与部署文档(多副本 + LB + 控制面对接);
4. 每实例分片语义(keypool 冷却/TPM/语义缓存)在 design 文档显式化:集群口径 = 实例级自治 + 控制面全局预算,分布式强一致限流不做(v1)。

## 范围修订(2026-09-11,用户裁决)

**支付不真实落地,预留抽象接线能力即可。** 据此:

- **账本与支付通道解耦**:控制面钱包账本只认「入账事件」(订单引用、金额、币种、来源、幂等键),支付仅是入账来源之一;
- **预留 `PaymentProvider` 抽象**(接口形态预估,实现推迟):`CreateOrder(金额, 主题, 回调地址) → 订单引用` / `VerifyWebhook(载荷, 签名) → 入账事件` / `QueryOrder(引用) → 状态`;
- 真实 PSP 接入 = 实现一个 provider adapter + 配置,**不动账本与订单域**——与 muniu 的 quirk/adapter 哲学同源:只声明差异,集成隔离在边界;
- 控制面 MVP 以「管理员手工入账」兜底(同样走入账事件,天然幂等),商业化闭环不阻塞 Phase 1;
- 未经真实落地的支付代码不做——避免「看起来支持实际没验证」的假接口风险,接线能力以契约测试 + mock provider 证明。

## 后果

- 正面:两形态各自的最优架构;网关安全面最小化;HA 标准化;商业化与基建的迭代节奏解耦;muniu 的采用门槛不变(one-api 的成功正来自单二进制零依赖,此优势必须保住);
- 负面:用户获得平台能力需多部署一个控制面(以「standalone 仍一等公民 + 控制面开源可选」对冲);跨仓契约(同步 API/key 格式/计量汇协议)需两仓共同遵守并以契约测试钉死——本仓 conformance 纪律的直接延伸。
