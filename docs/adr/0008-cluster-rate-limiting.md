# ADR-0008:集群限流语义——实例级自治 + 控制面全局预算

- 状态:已接受(2026-09-11);**修订(2026-09-13,openspec `cluster-ratelimit-shared-view`)**:cluster 维度部分推翻,见文末「2026-09-13 裁决修正」。

## 决策

cluster 形态下限流分两层:**实例内**沿用现有进程限流(RPM 滑窗/TPM/日配额,内存态,精确);**全局**预算由控制面承担(把 N 倍实例系数下发到各实例的载体限额/配置,或由控制面按聚合用量动态收紧)。分布式强一致限流(Redis 中心化令牌桶)v1 明确不做。

## 理由

- LLM 网关的限流诉求以「成本护栏」为主,非安全边界:瞬时超卖 N×(实例数已知且小)可控,由控制面按 `全局预算 ÷ 实例数` 收紧系数即可覆盖;
- 强一致分布式限流的代价(每请求一次中心往返或 Redis 依赖 + 失联策略)与其收益不成比例,且违反单二进制零依赖纪律——真需要时以 ADR 增补 Redis 模式。

## 后果

文档必须显式声明「限流为实例级语义,全局精度 = 预算收紧策略」;控制面产品负责全局预算的分摊与回收(跨仓契约)。

## 2026-09-13 裁决修正(部分推翻,openspec `cluster-ratelimit-shared-view`)

独立重审结论:**本 ADR 在 standalone 维度正确;在 cluster 维度把「不做强一致」偷换成了「不做任何共享」,推翻。**三条理由:

1. **过载保护反噬被保护对象**:实例独立计数使 N 副本实际放行 ≈ 上限 ×N(cluster-semantics.md 自认)。上游按账号限 RPM——网关限 60 实放 60×N,打爆上游账号并触发 failover 连锁:保护失效不是弱化,是让上游与账单直接承压。业界对照:Kong 限流插件(PG/Redis 共享计数)、APISIX(Redis)、Envoy(集中 rate-limit service)、LiteLLM(多副本明确要求 Redis)——「副本各自计数 + 事后纠正」做实时限流没有先例。
2. **与 ADR-0006「宁严勿漏」自相矛盾**:失联时恰恰没有控制面纠正兜底,而本地限额是松弛 ×N 的——最需要严格限额的场景(平台级故障),限额反而最松,日配额失去全局意义。
3. **未贯彻 ADR-0005 自引的 Nacos 先例**:「单机内嵌 Derby、集群外部 MySQL」的哲学是共享状态跟着形态走;该哲学落到了权威状态层,却没落到限流计数层。限流是漏桶不是闸门——需要的是**共享视图**,不是强一致(原子 INCR、轻微过限可接受);原裁决否决「强一致」顺手否决了「任何共享」,是概念偷换。

修正后决策:**限流计数后端可插拔**——standalone 缺省 inmem(语义零变更);cluster 配置可选 redis(原子 INCR + TTL 窗口,共享视图消除 ×N;redis 不可达降级回实例自治并告警——宁有弱限制,勿无限制)。mk2 载体限额语义不变(载体是「声明」,计数后端是「执行」)。落地载体:`cluster-ratelimit-shared-view`(实现与 platform-data-plane cluster 形态收尾联动)。被否决的备选:数据面整体换 PG(治标错位——×N 根因是计数器在进程内存而非存储引擎;毁单二进制叙事;副本有状态化违背 ADR-0005);维持原状(上述三问题真实);载体预收紧 rpm/N(仅作临时缓解)。
