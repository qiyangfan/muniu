# 压测报告:2026-09-10(muniu SSE 流式转发)

> 模板:docs/benchmarks/TEMPLATE.md。原始数据:`docs/benchmarks/raw-20260910-033943/`(oha --output-format json)。

## 方法

- 被测:muniu(本地构建,`scripts/bench/muniu-bench.yaml`:单上游假上游、计量管道开、RPM 限流开);
- 假上游:`scripts/bench/fake_upstream.py 59990 20 0.01`(20 chunks × 10ms 固定延迟,ThreadingHTTPServer);
- 负载:oha 1.16.0 同机执行,`run_oha.sh` 四档并发 100/500/1000/5000,每档 20×并发数请求,POST SSE;
- 对照组 one-api:**官方 v0.6.10 darwin-arm64 二进制,同机执行**(渠道指向同一假上游,SQLite 存储,官方默认配置;Docker 镜像无 arm64 故采用官方原生二进制,规避镜像架构问题)。

## 结论

1. **吞吐**:muniu 峰值 ≈ 3.85 万 rps@1000 并发(100% 成功率);one-api 在同剧本下吞吐稳定在 ~250-480 rps——**muniu 吞吐约为 one-api 的 80-150 倍**。one-api 的每请求令牌计数与配额预扣(SQLite 写)是其主要每请求开销;
2. **首字节延迟**:muniu p50 从 1.15ms(100 并发)到 17.28ms(1000 并发),随并发平滑;one-api 从 8.98ms 恶化到 1,748ms,p99 在高并发档超过 4 秒;
3. **稳定性**:muniu 四档全 100% 成功;one-api 5000 档 99.8%(吞吐腰斩,瓶颈在其自身每请求处理);
4. 计量落库为异步批量管道(500ms/256 条),压测全程无背压告警,未阻塞请求路径。

## 局限(如实声明)

- 负载机与被测同机,CPU 争抢使绝对数字偏高,**只做相对对比**有效;
- 5000 档假上游自身(线程模型)先于网关达到瓶颈,该档数字解读为「系统上限」而非网关上限;
- one-api 对照采用官方 darwin-arm64 二进制 + SQLite + 默认配置,未经专门调优;其令牌计数/配额预扣属功能差异而非缺陷;
- 未模拟 TLS 终结与反代链路(生产拓扑差异)。
