## Context

`internal/metering` 的 ingest 汇在下游返回 2xx 时报告传输成功；管道仅在传输失败时保留或重放本地缓冲。该契约适合可靠接收，但不能承担钱包业务补偿。锦官同名提案将先持久化不可变用量，再尝试扣账，并用已有明细恢复待结算记录。

## Decision

保留既有计量推送协议，只补清责任与验收。木牛的责任截止于控制面持久接收；是否完成钱包扣款，由锦官基于同一用量 ID 管理。

### 成功接收

锦官完成整批各行的持久接收后，可按现有协议返回 2xx，包含钱包余额不足的行。木牛将该批视为已投递，释放相应缓冲，不解析钱包状态，也不把 `skipped_insufficient` 转成网络重试。

锦官持久保存的 `pending` / `skipped_insufficient` 明细必须在其本地恢复；幂等扣款继续使用原 `refId`。此能力是锦官提案的交付要求，不能仅靠文档宣称恢复存在。

### 接收失败

网络错误或锦官不能持久接收全部有效行时，下游仍返回非 2xx；木牛按现有规则保留整批并续传。若批内前缀已入库，整批重投也必须由控制面同一用量 ID 去重，不能重复扣款。

### 停服与恢复

木牛继续按既有控制面拉取周期应用密钥 `suspended` 状态。Mock 充值入账解除停服、后续补账再次不足时重新停服，均由锦官产出最终状态；不引入网关直连钱包或即时刷新协议。验收记录须注明恢复任务与密钥拉取的收敛延迟，不能把充值响应解释为全部欠款已清。

## Cross-repository contract

- 对侧提案：`../jinguan/openspec/changes/recover-pending-usage-settlement/`（从木牛仓库根定位）。
- 保留既有 HTTP ingest 字段、签名、响应统计和用量 ID；新增财务恢复状态属于锦官查询面。
- 用例共用真实 Key ID、固定用量 ID、Mock 支付回调及钱包账本；不使用第二套测试支付接口。
- 两仓分别执行各自 `make check`，再验完整链路；不得用木牛测试通过代替锦官资金断言。

## Risks and mitigation

- 接收成功后没有补账实现，会继续漏结算：跨仓验收必须证明充值后历史待结算明细产生恰好一笔扣账。
- 一批部分持久化后网络失败会重投：覆盖原 ID 重放不重复计费。
- 支付后短时间内状态可能再次停服：按锦官钱包与欠款的实际结果判定，记录异步收敛。

## Validation

补充 ingest 汇 2xx / 5xx 的定向测试，复用现有缓冲续传测试；完整链路使用锦官 Mock 支付，检查原用量 ID、接收次数与资金账本，确认钱包恢复不伪造新的网关投递。
